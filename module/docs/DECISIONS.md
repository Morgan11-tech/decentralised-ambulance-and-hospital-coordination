# Modelling decisions — plain-English record

This document records **what was decided in building and testing the Twente ambulance model, and why**.
It is written for a reader who knows the project but not the code. The findings are in
`RESULTS_SUMMARY.md`, every number with its confidence interval in `../results/tables.md`,
calibration detail in `../results/calibration_report.md`, and sources in `REFERENCES.md`.

Values that are not taken from a source are tagged `[ASSUMPTION]` in `src/config.py` and here.

---

## 1. What is compared, and why

One simulated Twente region (11 ambulance posts; the two 24/7 emergency departments MST Enschede and
ZGT Almelo), run two ways on exactly the same emergencies:

* **A — Centralized.** A control room takes each call (with a limited number of operators, §4b) and
  sends the nearest free ambulance, most urgent call first. This mirrors how Dutch 112 dispatch works.
* **B — Decentralized.** No dispatcher. Each call is announced; free ambulances reply with their
  estimated arrival time (a "bid"); when the bidding window closes, the fastest bid wins. This is the
  Contract Net Protocol (Smith 1980). Calls are auctioned most urgent first (§6).

* **H — Hybrid (fallback), E4 only.** A while the control room is up; B while it is down; back to A when it
  recovers (§6b). It differs from A only during a dispatcher outage, so it is only run in E4.

**Both modes serve the most urgent calls first.** An earlier version also ran a plain auction without an
urgency order. It lost badly under load, but mostly for lack of triage, not for lack of a dispatcher.
That comparison was removed (§6), so the remaining difference is the coordination structure.

**Question:** under which conditions does decentralized coordination match or beat centralized, and
where does each break down? The aim was never to show that one is better. The literature is split
(Umam et al. 2019 favour decentralization; Deo & Gurvich 2011 show uncoordinated decisions can make
delays worse), which is why a controlled head-to-head is useful.

## 2. What the code does, and what was changed

| Where | What | Why |
|---|---|---|
| `src/` | The model: `config`, `model`, `agents`, `channel`, `incidents`, `metrics`, `viz`, `generate_incidents` | Shared by apps and experiments |
| `apps/` | `app.py` (experiment app), `voice_app.py` and `run_voice_incident.py` (one voice-agent incident) | Watching the model; link to the conversational agent |
| `experiments/` | `calibrate.py`, `run_experiments.py`, `analyze.py`, `experiment_core.py` | Calibration, experiments E1–E6, figures and tables |
| `results/` | `experiments.csv`, `figures/`, `tables.md`, `calibration_report.md`, `presentation/` | Outputs (all regenerated by the scripts) |

Changes to model behaviour, all behind config values so they can be varied:

* **Call processing for both modes** (§4), replacing 3 minutes that used to be added after the run.
* **Finite operators in the centralized control room** (§4b): calls queue when all operators are busy.
* **Urgency order in the auction, always** (§6). The plain auction and the on/off switch were removed.
* **Hybrid mode** (`mode="hybrid"`, §6b) with a sweepable switchover delay (`SWITCHOVER_DELAY_MIN`).
* **Auction timing options** (§5): whether the auctioneer knows the message delay, and an early-close
  rule. Defaults keep the original behaviour; neither option is in the current experiment set.
* **Bids carry the ID of the announcement they answer**, so a late bid for an auction that has
  already closed is discarded, as with the contract number on a Contract Net announcement (Smith 1980).
  With the default timing, every bid arrives in time, so this changed no default result.
* Smaller fixes: ambulance speed is read when an ambulance is created (so calibration can change it); the
  app sliders start at the calibrated fleet; the sample-incident fallback path points to `data/`.

## 3. Calibration — making the centralized baseline match reality

**What calibration means here.** Some inputs are published facts (the 15-minute norm, the urgency mix,
handover times). Others are not published as a single number: how many ambulances are on duty at any
moment, how fast they drive on average, how many ED places are effectively free for ambulance patients.
Those are `[ASSUMPTION]` values. Calibration picks them so that the model's *outputs* match real Dutch
*outputs*. No sourced number was tuned.

**Normal demand.** Twente had 23,238 A1 (incl. A0) dispatches in 2024 (Tweede Kamer 2025), i.e.
**2.65 urgent calls per hour**. A2 calls are added in the national mix, giving 4.25 emergency calls/hour.

**Targets.**

| Target | Real value | Source |
|---|---|---|
| 95th-percentile A1 response, call → on scene | 15–17 min (national 16:57; regions 15:08–18:20) | RIVM/VZinfo |
| Population within 12 min drive of a post | 98.1% | RIVM/VZinfo |
| Hospital arrivals with offload delay | 7.7%, median 16 min | WAITED 2025 |

RIVM's 98.1% is a **map-based coverage figure** (are posts close enough to people?), not the share of
calls on time. So coverage sets **speed**, and p95 sets **fleet size**.

**How.** 648 combinations (fleet 10–20 × speed 55–70 km/h × six ED capacities × three stay lengths), each
on 10 simulated days. The selection rule was fixed before looking: keep combinations that meet *all*
targets, take the *smallest* fleet among them, then the closest fit.

**Chosen values** (re-run after call processing (§4), after finite operators (§4b), and on 2026-10-28
after the clock fix (§9); the last run changed the ED values, see below):

| Parameter | Value | Justification |
|---|---|---|
| Ambulances on duty | **13** `[ASSUMPTION]` | Ambulance Oost has ~32 vehicles, but not all are staffed at once (shifts, A2 and planned transport, which the model leaves out). 13 is the smallest fleet that meets the norm. |
| Average speed | **60 km/h** `[ASSUMPTION]` | On-road speed; posts then cover 97.9% of residents within 12 min (target 98.1%). |
| Detour factor | 1.3 `[ASSUMPTION]` | Roads are ~1.2–1.4× longer than a straight line (Ballou et al. 2002). Only speed ÷ detour matters, so it is not tuned separately. |
| ED places MST / ZGT | **10 / 6** `[ASSUMPTION]` | Places effectively available *to ambulance patients* (walk-ins use the rest), not total beds. |
| ED stay | **195 min** `[ASSUMPTION]` | 3¼ hours. |

**Fit** (with 1 operator): p95 **16.1 ± 1.1 min**, coverage 97.9%, offload 8.6% (median 15.9 min, close
to WAITED's 16 and within its IQR 10–25). On 30 new days never used for calibration: p95
**17.5 ± 3.2 min** (17.4 with unlimited operators), above the 15–17 band but inside the real regional
range (15:08–18:20). It is reported as is, not re-tuned: re-tuning on the test days would be fitting to
them, and the calibration days are inside the band.

**Why the values changed from the first calibration** (13 units, 65 km/h, 9/6 places, 180 min): the old
combination still meets every target, but with simulated call processing (2 min instead of 3 min added
afterwards) its p95 fell to 15.0 min, the bottom of the band. The same fixed rule now prefers the
combination closer to the middle. Offload is very sensitive to ED places: one place fewer roughly doubles
it, which matches the clinical experience of "suddenly everything is full".

**Why the ED values changed again (2026-10-28)** (10/7 places, 210 min → 10/6, 195 min): before the clock
fix (§9), the last minutes of every simulated day had no new calls, so the days were very slightly
lighter than the target rate. With full days, the same fixed rule now prefers one ZGT place fewer and a
shorter stay. Both combinations fit the targets; fleet (13) and speed (60 km/h) did not change. The
offload median now fits WAITED better (15.9 vs 10.7 min).

## 4. Decision latency (call processing) — the same for every mode

**What it is.** The time from the 112 call to an ambulance being notified: taking the call, finding the
location, deciding the urgency. NASEMSO calls this "PSAP to Unit Notified" (NASEMSO 2024). It is separate
from turnout ("chute time": notified → driving).

**Value: 2 minutes** (`DISPATCH_HANDLING_MIN`). Measured call-to-dispatch in 13 Italian dispatch centres:
**2.3 ± 2 min** (Citerio et al. 2006, suspected-stroke calls). The Dutch norm budgets **3 minutes for
call handling and turnout together** ("12 minuten rijtijd + 3 minuten meld- en uitruktijd", RIVM/VZinfo),
so 2 min of processing fits inside it. Turnout itself is not modelled. Caveats: the measured value is
Italian, from 2006, and for stroke calls; no Dutch per-call figure was found.

**How it is modelled.** A call can be allocated by the dispatcher (A), or announced for bidding (B), only
after 2 minutes of processing. The ambulance is not held during that time, because in reality the unit is
chosen *after* the call has been processed. The bidding window comes **on top**: it is the genuine extra
cost of having no dispatcher. In A the processing also needs a free operator (§4b).

**What it changed.** The earlier version did not simulate this delay, but it added 3 minutes to every
measured response afterwards, equally for both modes. So the earlier comparison was not unfair to the
auction: the A–B gap is the same (~2 min). Now the delay happens inside the simulation, and the calibration
target is total response (call processing + travel). All results were regenerated.

## 4b. Finite operators in the control room — and the one deliberate asymmetry

**Why.** Before this change, the centralized control room could process any number of calls at once, so
it never queued under load. Real control rooms have a fixed number of call-takers on shift, and when all
are busy, callers wait. That queue is a second central bottleneck, next to the dispatcher outage (E4).

**How it is modelled.** `N_DISPATCH_OPERATORS` operators. A call holds one operator for the processing
time (`DISPATCH_HANDLING_MIN`, 2 min). If all operators are busy, it waits in a queue served **most urgent
first** (A0, A1, A2), then oldest first. After processing, the operator is free again and the call waits
for an ambulance as before. With unlimited operators the model reproduces the earlier results exactly
(checked run for run).

**Value: 1 operator** `[ASSUMPTION]`, derived from a source. Twente's calls are taken by Meldkamer
Oost-Nederland, which serves five regions (3.2 M residents). Its 112 ambulance team has 4 call-takers by
day, 4 in the evening and 3 at night, contributed pro rata by the five regions (Netwerk Acute Zorg,
MkON visit). Twente's population share (20%) gives 0.6–0.8 → 1. In reality the team is **pooled**, so
during a Twente surge up to 4 people could take its calls. That is why E6 sweeps 1, 2, 3, 5 and
unlimited. No per-region staffing report was found; the RIVM capacity model (2022) gives only a national
total.

**Simplifications.** One operator does both call-taking and dispatching. Real control rooms split
these roles (aanname and uitgifte). An operator is busy only for the 2-minute processing time, with no
after-call work or recovery time; the RIVM capacity model allows for recovery after distressing calls.
Both choices make the queue *shorter* than it would be in reality.

**The deliberate asymmetry.** Both modes pay the same 2 minutes of call processing. The *only* difference
is that in A the processing needs one of a few shared operators, so calls can queue for one, while in B
each call is processed independently, as if every ambulance crew could take its own calls. **This
asymmetry is the point:** it is what "a central control room" means in this model, and what B avoids by
having none. It may flatter B: someone still has to answer a 112 call in B, and the model gives B
unlimited call-takers. During a dispatcher outage (E4), call-taking in A carries on, because another
control room can take the 112 call while dispatch stays in the region (Netwerk Acute Zorg, MkON visit).
So the outage hits dispatch, not call-taking.

## 5. The bidding window — a design choice, not a physical cost

**Why it matters.** In the model, an ambulance computes and sends its bid in the same minute it hears an
announcement. So the window is not "time ambulances need to think"; it is how long the auctioneer
**chooses to wait** before deciding. A real radio/data auction could resolve in seconds.

**The trade-off.**

* A **short** window adds little delay, but risks deciding **before the bids arrive**, especially when
  messages are delayed or lost.
* A **long** window is robust, but adds a flat penalty to every call.
* "Wait until **every** free ambulance has answered" would be ideal, but the auctioneer would need to know
  who is free: a global roster, i.e. a central view, which breaks the decentralized premise. This is why
  Contract Net uses a fixed deadline: each announcement carries an "expiration time … a deadline for
  receiving bids" (Smith 1980).

**What is tested (E5).** The window is swept at 0, 1, 2 and 3 min at normal demand with perfect
communication, with centralized as the reference. It shows how much of B's everyday penalty is this one
design choice.

**Options kept in the code but not in the current experiment set** (they were tested in an earlier version
and dropped to keep the study focused):

* **Default rule** (`BID_WINDOW_KNOWS_DELAY = True`): the window is 2 min plus the known round trip. It
  never misses bids, but it assumes the auctioneer knows the delay, and it waits longer than strictly
  needed. That over-waiting is part of B's penalty in E3 (message delay).
* **Fixed timeout** (`False`): plain Contract Net. Bids that come too late are discarded. The earlier test
  showed that a fixed window shorter than the bid round trip misses *every* bid, because every bid sees the
  same delay.
* **Early close** (`AUCTION_EARLY_CLOSE = True`): close once bids have arrived and then a minute passes with
  no new bid, at most `AUCTION_MAX_WINDOW_TICKS = 10` min `[ASSUMPTION]`. It assumes units answer promptly
  and that bids arrive close together.

Smith notes that late bids "at worst … may result in a suboptimum selection". In this model a too-short
window is far worse: either all bids arrive in time or none do, and with none the call is announced again
and again without ever being assigned. E5's 0-min window shows exactly this.

**Resolution limit.** One model step is one minute (`TICK_MINUTES = 1`), so the shortest workable window
is 1 minute. Shorter windows would need a finer time step, which was not changed.

## 6. Urgency order in the auction (always on)

The centralized dispatcher has always served the most urgent call first. The auction now does the same,
permanently, with two rules (designed by us, not taken from literature):

1. Calls are announced and auctions decided most urgent first (A0, A1, A2, then oldest). An ambulance that
   has also bid on a still-open, **more urgent** call is kept for that call rather than given a less urgent one.
2. Cardiac-arrest (A0) auctions close after 1 minute (`IMMEDIATE_BID_WINDOW_TICKS`, `[ASSUMPTION]`, the
   earliest moment a bid can arrive), or sooner if the normal window is shorter.

Neither mode takes a unit off a call it is already driving to.

**Why the switch and its experiment were removed.** Earlier results showed that most of the plain
auction's penalty under load (87–89% at 1.5–2× demand) was the missing urgency order, not decentralization.
Comparing a triage-aware dispatcher with a triage-blind auction mixes two questions. With both modes
urgency-aware, the remaining difference is the coordination structure alone.

## 6b. Hybrid fallback: central dispatch, auction only while the control room is down (E4 only)

**What.** `mode="hybrid"` runs exactly as centralized (operators, nearest free unit, most urgent first)
until the dispatcher is unavailable. Then units self-dispatch by the urgency-ordered Contract Net auction
of §6 (Smith 1980). When the control room is back, it takes over again. Call-taking works as in A
throughout: as in the outage of §4b, another meldkamer keeps taking 112 calls, and during the fallback
it is what broadcasts the announcements. `[ASSUMPTION]`

**Switchover is not free.** A real fallback has to notice the failure and be switched on, and has to
notice the recovery to hand back. The model represents this with one number, `SWITCHOVER_DELAY_MIN`
(`[ASSUMPTION]`, default **0**). Self-dispatch runs only while
`outage start + delay ≤ t < outage end + delay`. So:

* for the first `delay` minutes of the outage **nothing is dispatched** (as in A), and
* for `delay` minutes after recovery units **keep bidding** before the dispatcher takes over.

**The default of 0 is a best case**, not a claim about real detection times; no source for those was
found. The model assumes failure detection and activation take `SWITCHOVER_DELAY_MIN`. The real value of
the hybrid depends on how fast an outage is noticed and the fallback switched on. That is why the delay
is swept (E4-switch: 0, 2, 5, 10, 20, 30, 50, 60 min at a 60-min outage, `[ASSUMPTION]` range; 50 is
roughly Twente's time to GRIP 2 in the 2019 112 outage [VRT-2019], 60 = the switch only comes once the
control room is back), and why the results
summary reports the delay caveat next to the hybrid finding.

**Boundary handling** (checked in code: no call is lost or assigned twice across 2 seeds × 3 delays, and
in a forced case with an auction still open at recovery):

* Both allocation paths read the same queue of released calls (`active_incidents`). A call waiting at the
  moment of a switch is simply picked up by whichever path runs next.
* **Auction open when the dispatcher returns:** it is left to close normally on its own deadline (bids
  still collected, no new announcements). If no unit wins, the call goes back to the queue, and the
  dispatcher takes it in the same minute. The dispatcher only touches calls in the queue, never calls
  in an open auction, and auctions are resolved first, so a unit can never get two awards.
* **Dispatcher award in flight when the outage starts:** the unit is already reserved and does not bid.

**Why only E4.** With no outage the hybrid **is** centralized, run for run (verified: identical results).
Adding it to E1–E3, E5 and E6 would only duplicate the blue line.

## 7. How the experiments are run, and why that makes the comparison fair

* **Same emergencies for both modes.** For each simulated day, A and B get the identical list of calls
  (time, place, urgency, on-scene time, whether transport is needed). Results are compared **in pairs**
  (e.g. B minus A on the same day), which removes most day-to-day noise.
* **30 days per setting** (the brief asked for ≥ 8). Every difference has a 95% confidence interval and is
  marked "n.s." when it could be noise. 10 days proved too few: in an early run, two outage curves seemed to
  cross, but the difference was within noise and vanished with 30.
* **Warm-up:** 4 hours not measured, so the EDs are not unrealistically empty; then 24 hours measured;
  then 2 hours to finish work in progress.
* **Response time = 112 call → ambulance on scene**, including call processing. A call still waiting at the
  end counts with the time it had waited (a lower bound), so overload is not hidden.
* **Headline metric:** p95 for A0+A1 calls (those the 15-minute norm applies to). A2 calls (30-minute target,
  Ambulancezorg Nederland 2019) are reported separately.
* **"High load"** for E3, E4 and E6 is chosen by a rule fixed in advance: the highest demand at which
  centralized still finishes ≥ 95% of calls. This is **1.25×** normal.
* **The experiment set** (trimmed): E1 baseline, E2 demand 1–5×, E3 message loss and delay (normal and high
  load), E4 dispatcher outage 0–120 min (high load; A, B **and H**), E4-switch hybrid switchover delay
  0–60 min (60-min outage, high load), E5 bidding window 0–3 min, E6 operators 1, 2, 3, 5 and
  unlimited (normal and high load). The fleet-size sweep, the outage at normal load, the unknown-delay window
  study and the priority on/off comparison were dropped.
* **Crossover:** the stress level where the curves swap order. It is only called a crossover when the
  difference is statistically clear on both sides, and it is reported as a range ("between 15 and 30
  minutes"), because the sweep has gaps.
* **Fairness metrics:** the urban–rural gap and the variance. The Gini index is reported but misleading
  here: adding the same 2 minutes to every call makes times *relatively* more equal without being fairer.

## 8. What the model measured vs what is argued from literature

| The **model measured** | **Argued from literature** (not simulated) |
|---|---|
| Response times (mean, p90, p95, % within the norm) | Whether crews could run an auction in practice |
| Unserved calls, utilization, diversions, offload | Dispatcher and crew workload, stress, training |
| Urban–rural gap, variance, message counts, bids per call | Legal responsibility without a dispatcher |
| Effect of demand, loss, delay, outage, window length, operator staffing | Survival value of minutes saved (e.g. Larsen et al. 1993); feasibility of a resilient data link |

Nothing in the right-hand column is a model result.

## 9. Main assumptions and limitations

* `[ASSUMPTION]` values (fleet on duty, speed, ED places and stay, detour factor, bidding windows,
  early-close cap, warm-up, operators on shift) are calibrated or chosen, not measured. Ambulance Oost does
  not publish hourly staffing.
* **Operators are modelled generously:** busy only for the 2-minute processing, no after-call work, one role
  for call-taking and dispatch. A real control room queues more than this one.
* **Abstract map:** straight-line distance × 1.3 at an average speed; no road network, traffic or time of
  day. Calls arrive at a constant average rate. One ambulance per call; ambulances are only available
  again once back at their post.
* Twente's A1:A2 ratio is assumed equal to the national one. WAITED is one Rotterdam hospital group, used
  as a plausibility anchor for offload.
* **Call processing is the same 2 min in both modes**, but only A needs a shared operator (§4b). Who takes
  the 112 call in B is not modelled; B effectively has unlimited call-takers.
* **Lost messages are noticed at once and retried** the next minute. Real radio loss is often silent. This
  flatters both modes, and the auction more, because it sends three messages per call instead of one.
* A broadcast announcement reaches all ambulances or none (one loss draw per message).
* Message delay is the same for every message (no jitter), which is what makes the early-close rule work so
  cleanly (§5).
* **Clock fix (2026-10-28).** Earlier runs started the model clock at each day's *first* call, which
  shifted the incident stream and left the last minutes of the measured day without new calls (on average
  15 min at 1×, up to 43). Experiments now start the clock at the start of the generated stream
  (`generate_incidents.BASE_TIME`); a single voice-agent incident still starts at its own call.
  Calibration and all experiments were re-run. Incident streams: `results/incidents_report.md`.
* **Hybrid (§6b):** a fixed switchover delay stands in for detection and activation; the auction's data
  link is assumed to survive the control-room failure. With delay 0 the hybrid result is a best case.

## 10. Reproducing everything

From the `module/` directory:

```bash
python experiments/calibrate.py        # ~2 min; writes src/config.py + results/calibration_report.md
python experiments/run_experiments.py  # ~2 min; results/experiments.csv (one row per experiment/mode/value/seed)
python experiments/run_experiments.py --only-e4   # ~20 s; re-runs E4 + E4-switch (with the hybrid) only
python experiments/analyze.py          # results/figures/*.png + results/tables.md
python experiments/export_incidents.py # results/incidents_report.md: arrival rates and the incident list per experiment
```
